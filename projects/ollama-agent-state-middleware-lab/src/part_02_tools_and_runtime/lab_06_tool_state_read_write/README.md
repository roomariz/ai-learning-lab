# 06 Tool State Read Write

## Goal

Show how tools can read from and write to structured agent state.

## What changed from Lab 05

Lab 05 saved and loaded state from disk.

This lab introduces simple tools that use state:

1. A read tool reads the learner's current status.
2. A write tool adds a learning note.
3. Another write tool marks the current topic as complete.

## Why this matters

Tools are not only for external APIs.

In production agents, tools often need to interact with state.

For example, a tool may need to:

1. Check the current workflow step.
2. Read the user's permissions.
3. Add a note.
4. Mark a task as complete.
5. Store a tool result.
6. Update the next topic or next action.

## Important limitation

This lab passes state manually into each tool:

```python
read_learning_status_tool(state)
write_learning_note_tool(state, note)
complete_topic_tool(state, topic)
```

This is useful for learning, but it becomes awkward as the project grows.

The next lab introduces the challenge more clearly, before moving to ToolRuntime.

## Expected behaviour

The exact assistant wording may vary because the response is generated by the local Ollama model.

The important behaviour is:

- Initial state contains learner profile and progress.
- The first tool reads from state.
- The second tool writes a note into state.
- The third tool marks tool_state_read_write as completed.
- Final state shows the updated note, completed topic, current topic, and last action.

## Learning point

Tool state access is powerful, but manual state passing can become repetitive.

When the answer can be derived exactly from state, the program should produce it deterministically instead of asking the model to interpret it.

This prepares the project for the next topic: why a runtime object is useful.
