# 03 Custom State

## Goal

Show how to define and use a custom state shape for a learning agent.

## What changed from Lab 02

Lab 02 stored one field:

```python
preferred_language: str | None
```

This lab stores a fuller learning profile:

```python
class LearningAgentState(TypedDict):
    learner_name: str | None
    preferred_language: str | None
    completed_topics: list[str]
    current_topic: str | None
    last_action: str | None
```

## Why custom state matters

Production agents usually need more than one memory value.

They may need to track:

1. Who the user is.
2. What the user is working on.
3. Which steps have already been completed.
4. What the current workflow step is.
5. What the last important action was.

This should be structured state, not loose text buried inside message history.

## Expected behaviour

The exact assistant wording may vary because the response is generated by the local Ollama model.

The important behaviour is:

1. The first call receives a fuller learning profile.
2. The program stores several fields in `LearningAgentState`.
3. The second call receives the custom state.
4. The assistant summarises the learner's current status from structured state.

## Learning point

Custom state gives the program a controlled structure for important agent facts.

Message history is useful for conversation.

Custom state is better for profile, progress, workflow status, permissions, task state, and tool results.
